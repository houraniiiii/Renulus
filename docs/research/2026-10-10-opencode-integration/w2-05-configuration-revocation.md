# Wave 2-05: Configuration activation and revocation

2026-10-10. Research only; no product changes. Rechecked [wave 1-04](w1-04-extensions.md) against OpenCode source **4b6fea2875e4f2e3e8a8fee181803e54f7056845**. Published **@opencode/sdk 2.0.26**, with Effect 4.0.0-rc.112, and tag **9b4ec5714d481559990db0a816d5dec19541a814** remain separate artifacts. [Package][npm] [Tag entry][tag]

**Recommendation:** activate immutable configurations through one Renulus authority; enforce current revocations at effect admission independently of upstream reload. This refines the [parent configuration section](../../planning/OPENCODE_V2_INTEGRATION_PLAN.md#one-configuration-authority), not a new framework or implementation approval.

**Observed source, not runtime proof.** Normal configuration priority is well-known → global directory → explicit file → direct project files → project configuration directories → supplied content. Managed policy separately reverses authored documents and appends organization statements; do not assume content wins every policy decision. [Configuration][config] [Policy][policy]

Plugin activation order is internal-pre → SDK-host → instance → configured packages → internal-post. Post includes configuration adapters, ending with guarded configuration-policy enforcement. Therefore an application transform is not necessarily final. [Supervisor][supervisor] [Built-ins][internal]

Package loading can call npm.add and import code **before** validating its exported plugin definition. Setup and cleanup also execute trusted code. Tool hiding cannot constrain those effects; approve complete, pinned plugin artifacts before import, with installation a separate explicit operation. Instructions, skills and retrieved text cannot grant installation authority. [Loader][loader] [Import][import]

MCP's generated wrapper asserts permission before callTool. Code Mode retains a separate callable inventory, so hiding individual model-facing definitions/catalog text does not remove nested capabilities; its nested calls still use that wrapper and its permission check. Direct **core** Mcp.Service.callTool has no equivalent permission assertion or visible-tool filter; this is not a claim that the public Promise plugin API exposes it. Code Mode additionally installs a fetch extension using globalThis.fetch without that assertion. Keep execute disabled initially, not merely MCP codemode:false. [Wrapper][wrapper] [Snapshot][snapshot] [Code Mode][codemode] [Direct call][direct] [Fetch][fetch]

Internal MCP recovery reconnects and repeats a call after session expiry, beneath an outer callTool decorator. Consequently, that decorator alone cannot prove permission rechecking on retry; enforcement must reach each connection dispatch. [Internal retry][retry]

**Proposed activation contract.**

1. **Stage:** create immutable version V with predecessor, artifact/build hashes, ordered configuration inputs, role/instruction/skill hashes, tool schemas, MCP endpoint/transport identity, purpose routes, retry limits and credential references. Record requested and effective versions separately. Freeze each version's source graph; never hot-replace host plugins shared by pinned sessions. Reject unspecified executable sources and mutable package aliases.
2. **Validate:** use managed roots and explicit Config/InstructionDiscovery replacements; eliminate ambient and well-known inputs unless deliberately included. Construct an unpublished candidate with recovery, provider dispatch, package acquisition and external MCP startup closed. Check schema/content hashes, required plugin health and the final effective registry digest after all transforms. A restored older generation is a failed candidate. Application-plugin setup alone is insufficient. Layer overrides and instance activation checks are existing seams; their complete containment is unproved. [Overrides][overrides] [Instances][instances]
3. **Activate:** after readiness is recorded, compare-and-swap the canonical active pointer from the expected predecessor to V; only then admit new work under V. Reconcile crashes between readiness, pointer commit and opening admission. Existing conversations retain their pinned versions. No candidate owns a second writer/recovery loop for the live runtime database.
4. **Adjust/rollback:** show the capability/endpoint/cost/retry difference and explicitly choose new conversations or migration of selected existing conversations. Quiesce/cancel affected work before migration. Failed validation preserves the old pointer; failure after activation closes affected admission and reconstructs the previous healthy version under **current** grants. Record both attempts; never restore revoked permissions or cancellation epochs. Upstream State.batch has no rollback, and failed plugin replacement can restore an older generation. [Batch][batch] [Fallback][fallback]

**Revocation and children.** Store monotonic grant/cancellation epochs outside the immutable version. Effective authority is pinned capability ∩ current grant ∩ operation scope; a child additionally intersects its parent's current effective authority and its requested subset. Recheck every dispatch, recovery/retry and domain commit, including direct calls. Child model overrides or appended session permission rules must not broaden that intersection. Preserve existing Python rights checks. Optional vLLM/Ollama/other providers require explicit version adjustment; subscription defaults and no required doctor setup remain. [Permission merge][evaluation] [Child selection][child] [Existing retrieval rechecks][retrieval]

Bind pending approval to operation/payload digest, config version, endpoint/schema identity and epochs. On reply, reread authority; reject stale requests without saving an “always” grant or releasing execution. Recheck at the effect boundary even after a valid approval. Selected upstream replies currently save/complete before reevaluation; only other queued requests are reevaluated afterward. Rejecting one request also rejects the session's remaining pending batch, which the UI must disclose. [Reply][reply]

Serialize revocation with durable effect admission: revocation winning that boundary means zero dispatch. An admitted external request is potentially sent and cannot be promised undone. Persist an operation/payload identity, endpoint/config/grant versions, remote idempotency reference when supported, and prepared/may-have-sent/confirmed/uncertain/cancelled-before-send outcome. Return an existing confirmed receipt on recovery; never blindly resend uncertain effects. Cancellation requests abort, waits for bounded settlement, and retains late-success receipts while preventing unauthorized publication. Disconnect/removal retains credentials; credential deletion is separate. [MCP lifecycle][lifecycle] [Abort forwarding][abort] [Recovery][recovery]

**Material parent-draft gaps.** “Instantiate and health-check” needs the closed candidate boundary: imports and MCP startup can have effects before pointer activation. “Atomic pointer” requires effective-generation verification and crash reconciliation. “Immediate revocation” applies before serialized admission, not retroactive remote cancellation. A receipt does not make an external server transactional.

**Smallest next proof.** Extend the existing MCP “waits for permission” path through real Tool.snapshot → Permission.assert/reply → counted synthetic MCP transport. Keep real Tool, Permission and Mcp services; move the fixture's MCP mock down to transport and supply synthetic session/config stores. Pause at approval, revoke, reply once/always, and require zero calls/no saved grant; repeat with a child and stale tool snapshot. Add direct-call and Code Mode negative controls. At the same seam, inject failed activation/fallback and rollback-after-revocation; require no widening. The upstream fixture and assertions were read, not executed. [Mock boundary][test-fixture] [Existing test][test]

Minimum proposed changes: a configuration activation adapter, mandatory dispatch/commit guards using existing domain checks, and receipt handling. Prefer embed.overrides/native executors; only if adopted built-ins escape those guards consider a narrow Permission.reply reevaluation patch. If host replacements cannot cover internal MCP retries, investigate a narrow pre-dispatch check inside recovering's run callback. No new scheduler. Actual override coverage, blocked candidate startup, cancellation settlement and packaged Windows behavior require the next proof.
