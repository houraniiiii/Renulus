# W1-02 — Existing learner memory and OpenCode integration

2026-10-10. Research and bounded synthetic testing only; no product implementation. **Recommendation: retain Renulus's Python memory service and canonical SQLite records. Fix dependency tracking before connecting automatic capture to OpenCode.** The highest-impact reproduced gap is that a completed answer can regenerate a subsequently corrected or deleted memory through a different evidence ID.

**Observed implementation, end to end.**

Failed/cancelled and case explanations do not produce that answer reference. [Repository][repository], [answer resolver][answer], [producer][learn] |

**Reproduced gap: suppression does not follow dependent answers.** An isolated inline Python probe used actual `LearnService`, `MemoryRepository` and SQLite, with deterministic recall/generation doubles. It seeded a learning point, completed an explanation that repeated it, and queued that explanation's `learn-answer:<run_id>` evidence. It then edited or deleted the original point before claiming the new capture. Both `current(job)` and `commit_capture()` accepted a supplied extracted candidate containing the old text, creating a new canonical ID. Edit left two facts; deletion left one resurrected-text fact while the original tombstone still existed. This establishes a commit-policy gap; supplying the extracted candidate does **not** measure how often a real model repeats it.

The cause is specific: recalled dependencies live only in `MemoryContext`; completed-answer evidence contains its own message/run/hash but no memory revision dependencies. `_suppress()` follows the original fact's linked source keys, not later answers that used it. Existing edit-during-answer checks protect the period before answer commit, leaving this later capture interval uncovered. Historical conversation replay also checks citations without memory dependencies. **Next wave:** persist reference-only dependency edges and validate them when admitting/committing capture and reconstructing context. Add the two post-completion regressions before extending capture to OpenCode. [Volatile pins][memory-context], [answer producer][learn], [suppression][mutations], [commit guard][outbox], [history replay][history]

**Other concrete gaps and limits.**

- **Generated teaching is not learner evidence.** Answer capture extracts the assistant's explanation, not the learner's demonstrated understanding. Facts have `learning-point`/`learning-evidence` labels, without structured extraction model/version, confidence/review status or passage-level source dependencies. Compaction is currently volatile reference text with no direct memory-write path; it must not become a new evidence producer simply because OpenCode persists summaries. Reviewed assessment separately retains correctness and fresh/assisted/repeat status. Preserve that distinction and add explicit generated origin/source lineage. Prompts asking the model not to infer competence do not validate accuracy. [Schema][schema], [extraction][providers], [context adapter][context], [assessment producer][assessment]
- **Scope is eligibility, not project isolation.** `ContextScope` contains only kind/entity ID; facts retain scope kind, and deduplication omits entity/scope. The probe added the same corrected text/topic/kind under entity B and obtained entity A's canonical ID. Retrieval checks whether the requesting scope is allowed but does not filter facts by its entity; Qdrant uses fixed profile-local user/agent IDs. This supports the existing personal memory pool, not demonstrated project/session isolation. Decide global versus project visibility before exposing tools; derive it from host identity rather than model-supplied scope. [Contracts][contracts], [insertion][insert], [engine][engine], [recall][recall]
- **Deleting a source chat and deleting retained learning are different operations.** Current thread deletion removes the thread and marks it deleted; capture subsequently rejects its evidence, but retained facts are not automatically removed. The UI exposes source references without an unavailable-source state or delete-related-learning flow. Design C already labels the latter behavior a planning default; it is unfinished integration work, not proof that all retained facts should cascade-delete. Backup reconciliation currently follows generic `*_id` references, which also needs review against independently edited/multi-source facts. [Thread deletion][thread-delete], [Memory UI][memory-ui], [C retention rules][c-retention], [backup][backup]

**Minimal OpenCode reuse plan; proposed, not implemented.** Keep one profile-owned `MemoryService`/Qdrant owner and its outbox. Do not construct a repository per subagent: its constructor resets running jobs. Register native recall/inspection tools and deliberate mutation operations around existing methods, preserving revision checks and idempotency. Automatic capture should follow an eligible domain commit, not arbitrary assistant/tool/summary events. OpenCode's [tool contract][oc-tools] supplies executable registration, cancellation signal and call/session identities; its [session contract][oc-session] permits context changes and a supplied compaction result. These are useful interfaces, not proof of invalidation or cross-process atomicity.

The next wave should resolve only three blocking integration questions: how completed OpenCode messages are referenced and verified without retaining a second authoritative transcript; how fact/source revisions invalidate dependent captures, active requests and persisted summaries; and which global/project/temporary permissions apply to parent and child sessions. Port the existing canonical-pin checks across that boundary. Retain current selected defaults; future optional providers need no memory-engine replacement.
