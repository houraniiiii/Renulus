# Wave 1-04: OpenCode v2 extensions and configuration authority

2026-10-10. Research only; no product implementation. Renulus checkout: 528025ff0b22477c12ee1512e0e7d15297a6e888, detached HEAD, with concurrent documentation changes left untouched. The user's current selection of the embedded OpenCode v2 harness supersedes older foundation recommendations. Future explicit opt-in vLLM/Ollama/additional providers remain possible; the selected subscription defaults and no required doctor setup remain unchanged.

**Conclusion.** Use supported plugins for learning capabilities, and a small host composition layer for discovery and authority. OpenCode supplies useful instruction, skill, MCP, permission and reload machinery. It does not supply an immutable Renulus configuration snapshot, universal permission revocation, or containment of executable plugins. The principal gaps are startup artifact selection, ambient discovery, policy-plugin failure and stale approvals.

**Supported customization.** The v2 Promise API provides asynchronous setup/cleanup, scoped registrations and synchronous transform editors for agents, tools, skills, MCP, providers/models, commands, references, integrations, VCS and web search. Native tools include executable functions, schemas, cancellation signals and progress. Session hooks cover context, titles, compaction, generation, retries and request customization; a supplied title/compaction result skips its model request. These are real v2 extension contracts, sufficient for most learning-role and domain-tool adaptation. They do not make storage, instance composition or execution coordination ordinary plugins. [Plugin contract][api] [Tools][tools] [Session hooks][session-hooks]

There is no public instruction-transform domain in the inspected plugin Context. Agent configuration and session-context hooks can supply learning instructions; internal instruction services separately manage discovered files and durable entries. InstructionEntry stores keyed session values and renders explicit replacement/removal notices. Read-triggered instruction injection uses paths in visible synthetic-message metadata as its deduplication ledger, allowing reinjection after compaction/revert. Neither mechanism is a content-versioned Renulus authorization record. [Plugin Context][context] [Instruction entries][entries] [Read-instruction ledger][ledger]

**Skills are instructions, not grants.** V2 supports embedded skill values plus configured directory/URL sources. File loading scans flat Markdown and nested SKILL.md files; IDs derive from filenames/directories, not frontmatter display names. Missing descriptions or autoinvoke=false omit skills from automatic guidance. The skill executor itself checks permission and loads the selected skill; autoinvoke=false is therefore not an execution deny. Built-in OpenCode/report skills also survive an empty application-plugin list. Propose bundled reviewed skill contents with manifest hashes, and explicit removal of irrelevant built-ins. [Skill sources][skill-config] [Parser][skill-parser] [Guidance filter][skill-guidance] [Executor][skill-tool] [Built-ins][builtin-skills]

**No-discovery has precise limits.** Core Instance.layer supports discovery:false, replacing Config and InstructionDiscovery with project/global discovery disabled. It preserves built-in plugins, well-known integration configuration, explicitly named files/commands and use-triggered behavior. The read tool still searches for nested AGENTS.md after successful reads. Consequently, discovery:false does not mean “no filesystem instructions,” “no connections,” or “no executable extensions.” [Instance options][instance] [Read tool][read]

The SDK's instances.configure result contains only plugins; its call to Instance.layer does not forward discovery. Public server configuration exposes project, directory, file and content, but no global/discovery switch. The SDK does expose a second embedding argument with layer overrides; server composition applies these after standard replacements. Thus strict no-discovery is a **host-layer task**, using explicit Config/InstructionDiscovery replacements and managed paths. For ordinary Library reading, use Renulus passage tools instead of granting generic read access with automatic instruction loading. No core fork is yet established as necessary. [Selector implementation][instances] [Server options][options] [Embedding seam][host] [Replacement ordering][routes]

**MCP is connected infrastructure with broad authority.** The inspected schema supports local command/cwd/environment and remote URL/headers/OAuth configuration, startup/catalog/execution timeouts, and explicit protocol negotiation. Code Mode defaults to enabled. Core reconnects expired sessions and maintains tools, prompts/resources and connection state. Removing a server closes its connection but intentionally retains credentials for later re-add. The generated tool wrapper asks permission using a sanitized server/tool action and resource "*"; this does not express Renulus document rights or argument-specific scope. Propose explicit server identities, codemode:false initially, bounded native domain tools, and separate disconnect/credential-revocation actions. [MCP schema][mcp-schema] [Connection removal][mcp-remove] [Tool wrapper][mcp-tool]

**Trust and reload are not transactional policy.** Package/local plugins are imported as executable modules and setup runs in process. Missing configured packages can reach npm.add. No sandbox boundary appears in this loading path; accepting a plugin means trusting its code, not merely approving its visible tools. Repository removal operations cannot disable the guarded OpenCode provider and configuration-policy plugins. Normal activation order places application plugins before internal post/config plugins, so a host transform must not assume it always runs last. [Module loading][module] [Runtime import][import] [Activation order][supervisor] [Guarded identities][guarded]

Reload rebuilds derived state from ordered transforms. A grouped transform failure removes that plugin's registrations; replacing a plugin whose setup fails can restore its previous healthy generation. State.batch coalesces notifications and explicitly does not roll back. Therefore plugin status, effective configuration and requested revision can diverge. The selector blocks failed supplied plugins during initial capability acquisition, but this is not proof that every later dispatch revalidates plugin health. Keep mandatory route/domain enforcement outside a transform whose disappearance could broaden capabilities. [State semantics][state] [Plugin fallback][plugin-failure] [Initial activation check][instances]

**Permission behavior and a concrete gap.** Rules use the last matching action/resource entry, defaulting to ask. Agent rules precede session rules; configured denial is checked before project-scoped saved approvals. A permission.evaluate hook can alter the remaining decision. The hook failure contract explicitly reserves a typed rejecting channel for tool execute.before, not every session hook. Do not infer a complete mandatory policy boundary from hook availability. [Evaluation][permission-eval] [Hook contracts][hooks]

A direct approval reply completes the selected pending request without calling evaluateInput again. Only other pending requests considered for automatic approval after “always” are reevaluated. Thus a permission change while a prompt waits needs a fresh check before the effect executes. Existing upstream tests cover configured-deny precedence and reevaluation of those other pending requests; they do not establish this selected-request revocation property. This is a **static gap**, not a reproduced runtime exploit. [Reply path][permission-reply] [Existing test source][permission-tests]

**One authority and session versions — proposal.** Let one Renulus configuration service own effective capability configuration in canonical records. Existing subscription/retrieval settings become inputs to that authority; avoid introducing an independently writable OpenCode configuration beside it. Store immutable versions containing role/instruction and skill-content hashes, plugin/build identities, tool and MCP identities, chosen provider/model routes and scope/retention policy. Store credential references only.

At session creation, bind the canonical session to a configuration version and put an opaque lookup reference in OpenCode metadata. Select instances with a profile/scope/version key; resolve that key through canonical records, never trust editable metadata as a grant. The SDK already caches by key plus Location and reconstructs plugins from saved metadata on restart. Same-key instances share lifetime state, and configuration runs on cache misses rather than every prompt. Missing/revoked versions must block capability acquisition rather than choose today's defaults. [SDK lifetime contract][sdk]

Pin ordinary configuration for the session; record explicit migration before widening it. Apply **current revocations immediately** at domain/model/MCP execution, including children and resumed work: effective authority is the intersection of the session version, present grants and operation scope. Changing a skill's contents or MCP endpoint must invalidate corresponding grants. Reload/unload should withdraw future access and settle owned work, but cannot erase already supplied model context or guarantee remote-effect cancellation. Reuse Renulus's existing rights/scope checks: retrieval already rechecks eligibility after embedding/search. [Existing rights][rights] [Retrieval checks][retrieval]

**Minimum changes to investigate next.**

- **Host composition:** supply explicit configuration/instruction layers, managed storage/paths and verified pre-recovery policy registration. Prove that hostile synthetic ancestor/global files, well-known sources and package declarations cannot add capabilities or cause unintended discovery/install/network activity.
- **Snapshot adapter and plugin health:** resolve immutable configuration into one reviewed plugin bundle; test changed keys, restart reconstruction, failed setup/transform, fallback generations and cleanup. Determine whether supported host overrides cover every required boundary before proposing patches.
- **Revocation:** retain checks in native domain executors and model dispatch; test a selected approval pending during revocation, saved grants, child scopes and replay. A narrowly scoped permission.reply reevaluation patch is a candidate only if host/executor checks cannot cover adopted built-in operations.
- **MCP:** test a synthetic server's capability changes, removal/re-add, endpoint identity, cancellation and credential deletion. Distinguish tool-list withdrawal from settlement of an in-flight call. Future optional providers need explicit activation policy, not incidental discovery.

These are next-wave investigations, not an implementation specification. Windows packaging, runtime containment, all-dispatch enforcement, atomic cross-domain reload, immediate revocation and instruction removal from already generated context remain **not proved**.
