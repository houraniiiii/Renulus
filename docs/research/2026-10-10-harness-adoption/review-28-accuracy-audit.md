October 10, 2026. Research only. Audited the synthesis and decisive claims in reviews 01–25, prioritising designs 21–23 and critiques 24–25. Public files were fetched over raw HTTP; ranges below count original LF-separated lines, including blanks. Renulus ranges were verified with `git show 528025ff0b22477c12ee1512e0e7d15297a6e888:<path>`: its public raw URLs returned 404 here, so the GitHub references identify locally available Git objects, not independently accessible public evidence. **Conclusion — judgment:** pi-durable remains a defensible first proof candidate, but its production suitability and comparative integration advantage remain unproved. Two corrections matter immediately: tool-hook failures have different semantics by hook and phase; published OpenCode startup ordering differs materially from the inspected branch. The synthesis's four blocking proofs remain necessary.

1. **Keep Pi's adoption units and delegation claims separate.** Agent-core requires an injected `streamFn`; AgentSession's SDK defaults to file-backed settings/history/resources and requires explicit assembly of CLI MCP/codemode extensions. Durable instead accepts `Models`, registry and optional execution environment; its package depends on pi-ai/Chord, not agent-core/coding-agent. Its owned-conversation/task machinery is real, while the illustrated model-facing subagent tool is application example code. The coding-agent subprocess delegate is another example. OpenCode v2 actually includes `SubagentTool.Plugin` in its built-in inventory. Therefore “Pi has only transcript persistence” is incorrect, and “Pi ships Renulus's subagent coordinator” is also unsupported. [P-agent][P-sdk][P-options][P-package][P-children][P-cli-child][O-builtins]

2. **Correct the synthesis's generic hook-failure claim.** At synthesis line 114 and review22 fact 4, qualify “ordinary hook failures do not block.” Durable's generic dispatcher reports non-abort exceptions, explaining why throwing from `beforeRequest` cannot enforce rejection. However, initial `beforeTool` execution catches exceptions, blocks the call, and revalidates changed arguments. Recovery's `execute` phase follows a different path: recorded/current policies must both be `safe`, then it directly reruns the implementation without repeating `beforeTool` or initial argument validation. Fresh authority/revision checks therefore belong inside every domain executor. Also, submission request-ID reconciliation compares type, not payload equality; the proposed digest binding is additional Renulus work. Neither contract guarantees exactly-once external effects or canonical publication. [P-hooks][P-tool][P-run][P-admission]

3. **Separate error retries, recovered generation and warming.** Reopen changes surviving running tasks to pending; scheduling is enabled globally by conveniences including submit/wait/abort. A recovered generation request invokes streaming again, independently of error-retry settings. Run/attempt correlation and a transport dispatch gate remain proposed integration, not established by injecting `Models`. AgentSession warming separately issues a one-token request with `maxRetries: 0`, swallows failures and may reschedule; that source does not establish warming in durable. The synthesis correctly limits the October 6 rule to visible authentication/quota/model/image rejection, preserves the current adapter's zero-SDK-retry proof baseline, and distinguishes DC16: validated generated-test work survives cancellation/restart without automatically restarting billed/model work. General transient-network/restart policy remains unresolved; safe deterministic reconciliation is separate. Hermes's failing custom-client hook selects the standard construction path, which alone does not prove a changed provider/model. [P-open][P-resume][P-generation][P-warming][R-rule][R-adapter][R-dc16][H-client]

4. **Ownership, retirement and Windows feasibility need explicit qualification.** Durable separates fork ancestry from ownership; background task boundaries survive ordinary conversation abort and are excluded from idle waits. Its write union has no conversation/entry deletion operation. Rewindable document retirement retains revisions; current-only retirement deletes revision rows. This verifies a missing coordinated purge contract, not impossibility of implementing one. SQLite storage explicitly assumes one process and supplies no cross-process lock; WAL/NORMAL protects process-crash commits while allowing newest commits to be lost on power/host failure. A Renulus profile lock, migrations and cross-store receipts/outbox reconciliation remain required host work. Node ≥22.19.0, optional environments and direct argv execution support native Windows feasibility; they establish neither a packaged single-owner host nor shutdown/recovery acceptance. Canonical SQLite/originals and the existing Python data engines retain their authority and value. [P-ownership][P-writes][P-retire][P-storage][P-package][P-argv][R-data]

5. **OpenCode artifact parity is substantively false for the inspected startup fragment.** Published `@opencode/sdk@2.0.26` exists, declares Effect rc.112 and lacks `gitHead`; default CLI 1.18.35 is a separate artifact. The inspected branch declares rc.118. Its host registers supplied plugins before starting recovery. In the verified published tarball, `dist/chunks/logging-d9bx5h6j.js` L38–40 starts recovery, while `logging-y51agw8v.js` L19–36 awaits host creation before registering plugins. Those fragments agree with the distinct v2.0.26 tag's source ordering; this does not prove whole-artifact/source parity. Qualify synthesis line 144/review23's ordering as inspected-branch behavior. An npm-based adoption cannot rely on startup plugin registration containing recovery; a preconstructed replacement layer or reviewed source build needs proof. Also correct review16's bare Effect citation to root `package.json` raw L83; L45–49 names companion packages. [N-sdk][N-cli][O-package][O-branch-host][O-tag-host][O-tag-promise]

**Reversal evidence — judgment:** reject durable as execution owner if recovery gating, fresh replay authorization or coordinated purge requires replacing substantial task/storage machinery. Prefer the embedded OpenCode alternative if a pinned artifact/source build passes those same controls with its integrated coordination intact; prefer controlled synchronous Hermes embedding if it passes with less maintained machinery. These are future comparisons, not measured advantages. Exact selected-subscription tool continuation and native Windows ownership remain untested; none of these source contracts demonstrates nephrology educational quality.
