# Review 03: OpenCode v2 runtime adoption seam

October 10, 2026. Renulus baseline: `528025ff0b22477c12ee1512e0e7d15297a6e888`. Inspected upstream: `anomalyco/opencode` v2 snapshot `55dde8810d8a859c0a21e42491ae7d5801fb49ef`. Code links below are immutable; ranges were counted from raw files. Comparison notes supplied leads. This is source inspection, with no installation, inference, runtime launches or acceptance testing.

**Conclusion — technical judgment:** OpenCode v2 can plausibly underpin an extensible Renulus learning harness with the application as one client. Adopting its coding UI is unnecessary. The embedded SDK is the clearest seam, but it retains directory/project semantics and stock coding services until deliberately configured or replaced. This is a conditional feasibility finding, not a foundation selection or permission to implement.

1. **Embedding is a real runtime boundary.** The host constructs the shared server graph, wraps its router in an owned in-process `fetch`, and closes the managed runtime with that transport. The Promise SDK builds the typed client on this transport without launching the CLI or listening on a network port. The Effect SDK exposes workspace lifecycle and layer replacements beyond the ordinary Promise facade. The protocol includes sessions, messages, events, permissions, MCP and plugin RPC alongside coding endpoints. These are built-in interfaces, not example plugins; the application can therefore be an independent client. 2. **Plugins offer substantial control, with residual coding coupling.** Stock inventory includes edit/patch/write, shell, agents, Plan and VCS. Config operations can remove plugins, including wildcards, except guarded OpenCode Console/provider and managed-policy plugins. SDK registration publishes updates across the host's booted Locations. Activation is ordered: internal-pre, SDK, instance, package, internal-post. The registry preserves unchanged ID/revision prefixes, closes changed registrations in reverse order, and activates replacements in child scopes; failures remain visible and can restore a previous healthy activation. This gives Renulus a supported replacement mechanism, but later configuration can affect earlier registrations.    The remaining structural coupling matters: Locations require absolute directories, and sessions require project IDs and directories. Non-Git directories receive directory-derived project identities. The instance graph still includes filesystem, shell, snapshots, VCS and watchers. Its `discovery:false` option suppresses ambient boot discovery while retaining built-in plugins; embedding needs deliberate wiring to obtain that profile. A learning “project” therefore cannot automatically be treated as an educational collection with the same identity rules. 3. **Host-controlled persistence does not supply Renulus domain authority.** Embedding defaults to `:memory:`; an explicit database path is needed for saved-by-default conversations. OpenCode owns its SQLite session/message/inbox/instruction schema and migrations. Plugin KV storage uses that same database and is namespaced only by plugin ID, so separate instances do not inherently separate learner data. **Proposed boundary:** give OpenCode an owned execution/transcript database and expose canonical Renulus source, learner and assessment services through scoped tools/RPC. Mem0 OSS, Docling HybridChunker, FastEmbed and LanceDB remain reusable domain assets, with Python integration work to assess. Derived indexes and transcripts must remain distinct from canonical local SQLite records; plugins' convenience storage is insufficient evidence of that separation. 4. **Distribution readiness is mixed, not “no V2 packages.”** The pinned source declares 2.0.26, Bun 1.4.2 and Effect rc.118. Public registry reads on October 10 returned `opencode-ai/latest=1.18.35` and HTTP 404 for `opencode-ai/2.0.26`, but **`@opencode/sdk/2.0.26` is published**, with Effect rc.112 and no `gitHead`. The v2.0.26 tag resolves to `9b4ec5714d481559990db0a816d5dec19541a814`, not the inspected pin. These identities cannot be conflated; a stable default npm CLI V2 release is not established. Upstream expressly changes plugin and server/client contracts. **Project judgment and uncertainties:** borrow the shared typed protocol, scoped plugin lifecycle and explicit runtime profile even if another foundation wins. Adoption depends on authorised Windows validation of a neutral SDK profile, domain-record isolation and packaging that matches the source pin. The host also automatically starts suspended-session recovery; enforcing Renulus's existing no-automatic-generative-retry rule remains unresolved, not a proposed permission change. Exact allowed Codex/Go account/model access is unverified by this interface review. No mandatory paid API, doctor-managed generative server or owner-hosted service is proposed. [startup recovery, raw L50–56](https://github.com/anomalyco/opencode/blob/55dde8810d8a859c0a21e42491ae7d5801fb49ef/packages/sdk/src/internal/host.ts#L50-L56).

Evidence that would strengthen the conclusion is a connected synthetic Windows embedding check proving those boundaries with the existing domain engines. Failure to suppress unwanted coding/discovery behaviour, preserve canonical authority or enforce the retained generation policy would weaken it. Educational quality across nephrology remains outside what these runtime interfaces establish.

Handoff: `docs/research/2026-10-10-harness-adoption/review-03-opencode-runtime.md` — conditional feasibility independent of coding UI; strongest fact: owned in-process transport uses the server graph; unresolved risk: neutral runtime/profile and generation-policy enforcement remain untested.
